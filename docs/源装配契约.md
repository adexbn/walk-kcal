# 源装配契约（草稿 · 待评审）

> **本文给谁看**：想接一个新数据源的同学，以及想搞清楚「这个数字是哪来的」的评委。
> 现状盘点 → [`服务商边界.md`](服务商边界.md)；怎么接一个源 → [`扩展开发.md`](扩展开发.md)。
>
> **状态**：**已部分实施（2026-10-15）**。§七 的「渠道启用制」已落地并测试；
> §一~§六 的三槽组装路径**仍未实现**（现有两个渠道都是「三合一」，用不上）。
> 决策与实施状态见文末 §十一、§十二。

---

## 为什么要有这份契约

现在我们把「数据从哪来」建模成**两个 provider**：`geo`（店在哪）和 `corpus`（多少卡）。

这个模型漏了一样东西：**「这家店有什么菜」**。它现在没有自己的接口，而是搭 `geo` 的便车——跟着 `nearby_dining()` 一起返回。后果是上一轮百度实测暴露的：

```
百度不提供推荐菜 → 整条链路退化，50 家门店被全部剔除，出一张 480×916 的废图
```

修的时候我打了个补丁 `GeoProvider.provides_dishes = True/False`。
**那个补丁承认了「推荐菜是独立能力」，却把它挂在了地图 provider 身上。** 本契约就是把这个补丁拆对。

---

## 一、三个槽

把「数据从哪来」拆成**三个互相独立的槽**。每个槽问一个问题、有自己的接口形状。

| 槽 | 问什么 | 接口形状 | 现在实现在哪 |
|---|---|---|---|
| **place** | 店在哪 · 多远 | `f(位置) → [店]` | ✅ `GeoProvider.nearby_dining()` |
| **menu** | 这家店有什么菜 | `f(店) → [菜名]` | ❌ **没有独立接口**，搭 place 的便车 |
| **heat** | 这道菜多少卡 | `f(菜名) → 卡数` | ✅ `CorpusProvider.heat()` |

**槽由「我们需要什么」定义，不由服务商定义。** 这是全文最重要的一条——它决定了新能力到来时会发生什么（见 §八）。

---

## 二、三个接口

一个源**实现哪些方法，就说明它供哪些槽**。

```python
class PlaceSource(object):
    supplies = frozenset({'place'})

    def stores(self, lon, lat, radius_m):
        """位置 → 店列表。同步阻塞，必须自己限速（见 §六）。"""

    def walk_route(self, from_lonlat, to_lonlat):
        """可选。真实路网距离 {'distance_m': int, 'duration_s': int}。
        返回 None = 不支持，上层退化为直线距离。"""

    def industries_of(self, raw):
        """店的一家店/一条原始记录 → 归一化业态列表。返回 [] 是合法的（见下）。"""


class MenuSource(object):
    supplies = frozenset({'menu'})

    def menus_of(self, store):
        """店 → 菜名列表。**只给菜名，不给热量**（热量是 heat 槽的事）。"""


class HeatSource(object):
    supplies = frozenset({'heat'})

    def heat(self, dish_name):
        """菜名 → {'kcal': int, 'label': str} 或 None。None = 没这个数据。"""
```

### 各槽返回的数据形状

**place 返回的一条店**（最小公约数——**够跑就行，不追求填满**）：

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 唯一标识，去重用 |
| `name` | ✅ | 店名 |
| `lon` / `lat` | ✅ | **GCJ-02**（provider 负责转）|
| `distance_m` | ✅ | 到中心的距离 |
| `address` | ○ | |
| `industries` | ○ | 归一化业态列表；**报不出返回 `[]`，但别瞎猜** |
| `category_hint` | ○ | 品类线索（「牛肉面」这种，供 L3 兜底）|
| `cost` / `rating` | ○ | 人均 / 评分 |
| `raw` | ✅ | **原始响应原样带上**。新源的特殊字段放这儿，不要塞进上面的通用字段 |

`raw` 是这套契约的**逃生舱**：我们不再为「将来可能出现的新字段」预留位置，需要时从 `raw` 里取。

**menu 返回**：菜名字符串列表，如 `['麻酱捞面', '小牛汤', '炸猪排']`。

**heat 返回**：`{'kcal': 450, 'label': '菜谱推算'}` 或 `None`。

## 三、装配规则：链式解析（唯一一条规则）

每个槽配一条**有序的源链**。取值 = 沿链依次问，**第一个给出非空结果的源胜出**；全空则该槽为空。

```
place 链：位置 ──▶ 离线快照 ──空──▶ 高德 ──空──▶ 麦当劳 ──▶ 得店列表
menu  链：  店 ──▶ 高德推荐菜 ─空──▶ 自带菜品表 ─空──▶ 麦当劳 ──▶ 得菜名
heat  链：菜名 ──▶ 下厨房语料 ─空──▶ （政策层兜底，见 §五）
```

一条规则，应用三次。**没有任何按源类型的分支。**

```python
stores = place_chain.resolve(lon, lat, radius_m)      # 第一个非空
for s in stores:
    s['dish_hints'] = menu_chain.resolve(s)           # 第一个非空
    for d in s['dish_hints']:
        d['kcal'] = heat_chain.resolve(d)             # 第一个非空
```

**「一次调用还是两次调用」由链自然表达，不需要两套接口**：

| 源 | 在哪些链上 | 额外请求 |
|---|---|---|
| 高德 | place + menu | **0**（`menus_of()` 复用 `stores()` 那次响应，见 §六）|
| 百度 / 腾讯 | place | 0（不在 menu 链上，跳过）|
| 大众点评 / 自带表 | menu | **每店 1 次** |
| 下厨房 | heat | 0（本地表）|
| 麦当劳 | place + menu + heat | 0（离线快照）|

## 四、`supplies` 的角色：声明，不参与控制流

`supplies` **不是**用来让装配层分支的（那就退回类型分支了）。它只有两个用途：

1. **启动自检**：源声明了 `'menu'` 却没实现 `menus_of()` → **启动就报错**，而不是在循环深处抛 `NotImplementedError`
2. **「源装配」报告**（见 §七）

★ 它同时**取代**了现在那个挂错位置的 `GeoProvider.provides_dishes`——那玩意儿就是 `'menu' in supplies` 的低配版，而且挂在错的对象上。

## 五、政策层与源层的分界：`prior` 往上挪一格

现在 `corpus.lookup()` 里混了两件事：

| | 是什么 | 应该在哪 |
|---|---|---|
| L1 语料命中 | **源给出的实据** | heat **槽内** |
| L2 菜名定品类 / L3 门店类型定品类 | **我们自己的估算政策** | heat 槽**之上** |

契约把它们分开：

```python
kcal = heat_chain.resolve(dish)          # 源层：L1，有依据的数
if kcal is None:
    kcal = prior.estimate(dish, store_context)   # 政策层：L2 / L3
# 还是 None → 弃权
```

**为什么值得分**：`prior` 不是「谁给我们的数据」，是「我们自己的推断规则」。混在源里会让人误以为换语料源就能换掉 L2/L3——其实那两层与语料源无关（这正是我们说的「换语料不会把覆盖率打回原形」）。

政策层自己带来源标签（`品类估算` / `同类估算`），所以「**每个数字带来源标签**」这条原则不受影响。

## 六、成本：必须显式声明，且有保险丝

链式解析让「成本」变得不直观，得把它摆到明面上。

| 声明 | 含义 |
|---|---|
| `menu_cost_per_store` | `0` = 复用已有响应；`1` = **每店一次请求** |

★ **高德的 `menus_of()` 是「缓存优先」**：`stores()` 那次响应里的推荐菜会被存下来，`menus_of()` 先查缓存（命中 → 0 请求）。**冷缓存时**（店来自快照、而非刚由同一 provider 返回）退化为每店 1 次详情请求——200 家店就是 200 次。

这是**正确行为**（该查就得查），但必须有保险丝：

- 调用方按 `menu_cost_per_store × 店数` 预估耗时，**超过阈值就报警并询问是否跳过 menu 槽**
- 所有 provider 的请求统一走 `walkkcal/geo.py::RateLimiter`（已有，默认 1 秒/请求）
- 记住这条教训：**并发超限不报错**。百度那次是我们贴着上限跑了几百次，才收到一条短信。

## 七、怎么声明装配

### 实际实现：**渠道启用制**（一个渠道 = 通用插槽）

默认模型是「**一个渠道同时给店铺 + 距离 + 菜品**」。启用哪些渠道由环境变量
`WALKKCAL_PACKS` 决定，注册表在 `packs/registry.py::CHANNELS`。

```bash
# 不设                        → 默认 mcd,nearby
WALKKCAL_PACKS=mcd            # 只启用麦当劳
WALKKCAL_PACKS=nearby         # 只启用周边餐厅（即「只要高德」）
WALKKCAL_PACKS=mcd,nearby     # 两个都启用 → 合并进同一个列表
```

**麦当劳默认启用**，因为这是麦当劳程序员节参赛作品。

| 想做什么 | 怎么做 |
|---|---|
| 加一个渠道 | `CHANNELS['你的'] = lambda: YourPack()`；要默认启用就加进 `DEFAULT_CHANNELS` |
| 未知渠道名 | **明确报错并列出可用值**，不会静默忽略 |
| 两个渠道同时启用 | 自动合并（麦当劳不占本地店配额，见 `select.py`）|

### 运行期输出「源装配」

跑渲染或 `python packs/registry.py` 时打印：

```
源装配：麦当劳(店✓ 菜✓ 热✓官方) ｜ 周边餐厅(店✓ 菜✓ 热✓估算)
```

这一行同时解决三件事：

1. 评委一眼看懂架构，不用翻文档
2. **退化变得可见** —— 换到不提供推荐菜的渠道、或只剩麦当劳时，这行会写清楚，
   而不是静默变空
3. 它是已有原则「**每个数字带来源标签**」（L1/L2/L3）**上移一层**的应用，不是新概念

所有渠道都不供推荐菜时，追加一行告警：

```
   ⚠ 没有渠道提供推荐菜 —— 只会展示「门店 + 距离 + 业态」
```

### 备用路径：三槽自己组装（本文件 §一~§六，**尚未实现**）

当一个渠道**凑不齐三样**、又不想为它写一个整体包时，可以按 §一~§三 把它拆成
`place` / `menu` / `heat` 三个单槽源再组装。

★ 这条路径**目前没有实现** —— 现有两个渠道（麦当劳、周边餐厅）都是「三合一」，
用不上。保留契约是为了让后来者有据可依，**而不是现在就建三个抽象层**。

> 注：原计划用 `WALKKCAL_PLACE` / `WALKKCAL_MENU` / `WALKKCAL_HEAT` 选三个槽。
> 现在没走这条路，所以 **`WALKKCAL_MENU` 的命名冲突不必解决了**
> （它继续指 `data/menu.json` 的路径）。真要上三槽时再谈。

## 八、明确不做的事

| 不做 | 理由 |
|---|---|
| **不加第四个槽** | 业态（`industries`）是 place 槽的**附属产出**（对同一个 POI 响应的解释），且 `filter` 有店名兜底。为对称而拆是过度设计 |
| **不做「按调用形状分接口」** | 按输入分形状会漏掉「按店查」的源（点评 / 自带表）。形状 2 种够用，组合靠链表达 |
| **不做大而全的数据 schema** | 字段填不满的地方迟早会被**编造**。只保最小公约数 + `raw` |
| **不为未知能力预留字段** | 见下 |

### 关于「将来出现全新能力」

你的担心是：新能力既不像高德也不像点评，那准备的抽象岂不是白费？

**能力抽象不会白费，因为它是加法。** 新能力来了不问「它像谁」，只问「它填哪个槽」。填不了就**加一个槽**（place 旁边再开一列）——老槽一行不改，因为**槽之间不耦合**。

真正会白费的是**数据模型做大**：一套 30 字段的大 schema，新能力无处安放，而且每个源都要努力填满它。

**所以我们的姿态是：预留「加槽的机制」，不预留「槽」本身。**

> 判据（两个门槛都过才值得抽象）：
> ① 它是否已被**真实变化**逼出来过？（不是「将来可能」）
> ② 它现在**有几个 occupant**？（≥2 才算真；1 个 = 投机）
>
> 按这条，place 4 个、menu 3 个、heat 2 个 → 都过。
> 而 `packs/` 与 `geo`+`corpus` **重叠**的抽象（同一个概念两套表示）→ 该收。
>
> ⚠ **反面别搞错**：`geo_template.py` / `corpus_template.py` / `pack_template.py`
> 都**没有任何 importer，而这是正确的**——它们是**给人抄的文档模板**，不是抽象接口的
> 唯一实现（`providers/__init__.py` 里写着「桩文件也是文档」）。
> **不要因为「零引用」就把它们删掉。** 判据里的「occupant」指的是**真实可用的实现**，
> 不是模板。

### 一条精确的边界

> **数据可以绑定服务商，代码不行。**

`data/*.json` 就是高德原始产物——**没问题**，因为 `snapshot.py` 把它一次性翻译掉，耦合止步在那里（防腐层）。
但**代码里不能出现 `keytag`、`餐饮服务`**，因为同一份代码要在多个源上跑。已有 `test_provider_boundary` 用 AST 扫通用层的非 docstring 字符串守着这条。

## 十、验收标准

契约算「做到了」，当且仅当：

| # | 断言 | 为什么 |
|---|---|---|
| 1 | **三槽各测一次「缺失」**，链路不崩、降级可读 | 参数化，不是 3×3×N 全组合（会爆）|
| 2 | 链式解析：第一个非空胜出；全空则该槽为空 | 唯一装配规则 |
| 3 | 声明与实现一致（`supplies` 有 `menu` 就必须有 `menus_of`）| 启动自检 |
| 4 | **完全无推荐菜的源**仍能出图（门店模式）| 百度实测踩过 |
| 5 | 对照组：**有推荐菜的源**口径不松（不因缺菜剔除门店）| 防「修百度顺手放松了高德」|
| 6 | 「源装配」行如实反映当前链 | 退化必须可见 |
| 7 | 通用层无服务商私有词汇（AST 扫描）| 已有，不能退 |
| 8 | 每个 occupant 单独可用（place 4 / menu 3 / heat 2）| 抽象不空转 |

## 十二、实施状态（2026-10-15）

**已做**：

| 项 | 位置 |
|---|---|
| 渠道启用制（默认麦当劳 + 周边，可配置、多个自动合并）| `packs/registry.py` 的 `CHANNELS` / `enabled_names()` / `get_packs()` |
| 「源装配」运行期输出 | `packs/registry.py::describe()`；渲染与自检都会打印 |
| 能力声明归位到**渠道** | `BasePack.provides_dishes`；`NearbyDiningPack` 委托当前地图 provider |
| ★ **安全带回溯**（不靠声明，靠数据事实）| `walkkcal/render.py`：整批门店一道推荐菜都没有 → 自动退回「门店模式」|
| 删死代码 | `BasePack._estimate`、`BasePack.nutrition_of`、`McdPack.nutrition_of`、`CorpusProvider.all_dishes` |

**未做（有意）**：§一~§六 的三槽组装。当前没有「凑不齐三样」的真实渠道
—— 百度属于这一类，但它已经能靠「门店模式」+ `data/menu.json` 处理掉。

**真要上三槽时的顺序**：
① 抽 `menu` 槽（把 `provides_dishes` 换成「链是否为空」）
→ ② `prior` 政策层上移 → ③ 引入 `WALKKCAL_MENU` 等选择器（届时再谈命名冲突）。
