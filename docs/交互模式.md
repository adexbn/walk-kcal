# 交互模式 · Skill / MCP / Bot 怎么和人对话

> **本文给谁看**：评委，以及想复用这套交互设计的同学。
> 想跑起来看效果 → [`../README.md`](../README.md)；想换数据源 → [`扩展开发.md`](扩展开发.md)。

## 一句话总纲

> **图是结论，话是推理，选项是下一步。缺任何一个，对话就断了。**

---

## 一、为什么这事值得单独设计

本项目的主交付物是**一张竖屏长图**。而对话是**多轮、渐进**的 —— 天然冲突。

最常见的错误是「只返回一张图」：

```
用户：吃什么
系统：[长图]
用户：……然后呢？
```

图给了**答案**，却没给**下一步**。用户看完不知道该干嘛，对话就死在这里。

我们采用业界主流的 **渐进披露（progressive disclosure）**：

**先给一个能用的答案，再把「还能怎么调」摆在手边** ——
而不是先问清楚（「你想吃什么菜系？」）再给答案。

| 范式 | 长什么样 | 问题 |
|---|---|---|
| 命令式 | `/food` → 出图 → 结束 | 用户没法细化 |
| 表单式 | 连环问：菜系？距离？价位？→ 出图 | 用户在第 2 个问题就走了 |
| **渐进细化** ★ | 随口一句 → 默认结果 + 2~3 个选项 → 点/说 → 细化 | 无 |

## 二、三轮对话流程

```
第 1 轮 · 零参数触发
  用户：「我今天中午只想吃 350 卡左右的午餐，有什么推荐的吗？」
  系统：长图 ＋ 一句话 ＋ 3 个选项      ← 不反问！

第 2 轮 · 细化
  用户：点「只想吃快餐」（或直接说「只想吃快餐」）
  系统：细化后的图 ＋ 新的选项

第 3 轮 · 收敛
  用户：「就这家吧」
  系统：文字详情（不必再出图）
```

**三条铁律**：

1. **零参数必须先出结果** —— 用户说「吃什么」时**不要反问**，直接给默认结果 + 选项。
2. **用选项引导，不罗列参数** —— 说「只想吃快餐」，不说 `industry=快餐|小吃|西餐|…`。
3. **选项要动态** —— 从当前数据算出来（K11 咖啡多就提示咖啡），不是写死的。

★★ **文案一律第一人称口语（2026-10-15 定）**：选项写的是**用户会说的话**，
不是系统给的动作名。理由：这些标签会直接变成按钮文字，
写成动作名是**机器的口吻** —— 用户是在「执行一个命令」，
写成第一人称则是**接着自己的话说**。

| 旧（动作名） | 新（人话） | `kind`（不变） |
|---|---|---|
| 换一批 | 我想看看别的 | `page` |
| 只看快餐 | 只想吃快餐 | `industry` |
| 别走太远 | 不想走太远 | `radius` |
| 看全部 | 都看看 | `reset` |

★ 连带的回问句（助手那一方）也要改成第二人称 —— 同一件事，
从谁的口里说出来不一样：按钮是「我想看看别的」，回问是「要我再翻一批给你看看吗？」。

## 三、一次调用返回什么：四件套

| 字段 | 内容 | 给谁看 |
|---|---|---|
| `text` | 一句话，三段式「结论 ｜ 依据 ｜ 下一步」 | 人和 Agent |
| `image` | 竖屏长图 | 人 |
| `meta` | `total / shown / page / pages / keyword` | Agent（决策用） |
| `next` | 2~3 个建议的下一步参数 | 用户（转问句或按钮） |

实现：`walkkcal/reply.py` 的 `build()`。

**`text` 长这样**（2026-10-15 口语化后的真实产出）：

> 按 350 卡给你挑。附近 105 家餐厅，我挑了 87 家（另有 18 家只卖饮品或甜点的，
> 先没算进来），先看第 1 批（共 6 批）。这一批主要是中餐本帮（10 家）、
> 火锅烧烤（2 家）。最推荐「大富贵酒楼(博兴路店)」：走 543 米，有 4 道菜在额度内。
> 「麦当劳(浦东融创精彩天地餐厅)」也在这一批：走 807 米，它家的热量是官方给的实数
> （别的店只能估算）—— 麦香鱼 325 卡、薯条（中）337 卡、迷你草莓新地 122 卡，
> 都在额度内。要我再翻一批给你看看吗？

★ 语言规则：**说发生了什么，不说我们怎么实现的**。数字一个不少，但
「进入候选」「封顶」「品牌最多占 1/3」这类内部术语一律不出现。

**`next` 长这样**：

```python
[{'label': u'只想吃快餐',   'kind': 'industry', 'params': {'industry': u'快餐'}},
 {'label': u'不想走太远',   'kind': 'radius',   'params': {'radius_m': 500}},
 {'label': u'我想看看别的', 'kind': 'page',     'params': {'page': 1}}]
```

生成逻辑：`walkkcal/hints.py` —— **从当前数据动态算**，且有优先级：
我想看看别的 > 只想吃最多的那个业态 > 不想走太远。最多 3 条。

## 四、三个入口的分工 —— 关键区别是「有没有 Agent」

| | 谁解析用户的话 | 谁组织回复 | **你要做什么** |
|---|---|---|---|
| **Skill** | Agent | Agent | 把**参数映射和追问规则**写进 `SKILL.md` |
| **MCP** | Agent | Agent | 把**参数和用法**写进 tool 的 `description` |
| **Bot** | 你自己 | 你自己 | 把选项做成**按钮** |

**Skill 和 MCP 的本质是「给 Agent 一份说明书」** —— 你不需要设计对话，Agent 会设计。
你要做的只是让能力**可被发现**：

- `SKILL.md` 的 `description` → 决定**什么时候触发**
- `inputSchema` 里每个参数的 `description` → 决定 **Agent 知不知道你支持这个参数**

> 反直觉但重要：**MCP 的 schema 不是给程序看的，是给 Agent 看的。**
> 所以我们在参数说明里写的是「用户说『只想吃快餐』时填这个」，
> 而不是「industry 字段，类型 string」。

**Bot 没有 Agent**，对话设计完全落在你身上 → 必须用按钮把选项摊开。

### 「下一步」放哪？按转化率排序

| 路径 | 放哪 | 转化率 | 什么时候最有用 |
|---|---|---|---|
| **按钮 / 快捷回复** | Bot 的 inline keyboard | 最高 | 有对话界面时 |
| **对话文本** | 回复最后一句 | 中 | Skill / MCP / Bot 都适用 |
| **图里（脚注）** | 长图底部 | 最低 | **图被转发出去**、接收者没有对话上下文时 |

最后一行容易被忽略：**图里那行提示真正服务的场景是「这张图被转发到群里」**。

## 五、参数映射（三入口共用同一份语义）

| 用户这么说 | 参数 |
|---|---|
| 「吃什么」「附近有什么」 | 零参数调用 |
| 「只想吃快餐」「附近有什么西餐」「想吃日料」 | `industry=快餐/西餐/日料…` |
| 「不想走太远」「就近」「500 米内」 | `radius_m=500` |
| 「还有别的吗」「换一批」「再看看」 | `page` 加 1 |
| 「这家怎么样」 | 出**纯文字详情**，不必再出图 |

三入口的实现：

| 入口 | 怎么实现 |
|---|---|
| Skill | Agent 读 `SKILL.md` 的映射表，自己把自然语言转成参数 |
| MCP | Agent 读 `inputSchema.description`，自动填参数 |
| Bot | 按钮的 `callback_data`（`i=快餐` / `r=500` / `p=1`） |

## 六、业界参考

| 产品 | 返回什么 | 「下一步」怎么给 |
|---|---|---|
| Telegram Bot | `photo` + `caption` | inline keyboard 按钮 |
| Slack App | Block Kit：`image` + `section` + `actions` | actions block 按钮 |
| 微信公众号 | 图文消息（多图文卡片） | 卡片里嵌链接 / 小程序 |
| GPTs / MCP Server | `content[]` 多块 + `structuredContent` | 模型自己组织成话 |
| CLI（`gh` / `kubectl`） | stdout 文本 | 末尾一行 `Run X to ...` |

**共同点：没有任何一个主流产品只返回一张图就结束。**

## 七、五个反模式

1. ❌ **只出图不说话** → 对话断裂
2. ❌ **罗列全部参数** → 没人读
3. ❌ **一次问一堆**（表单式）→ 用户流失
4. ❌ **选项写死** → 点了发现没结果
5. ❌ **图里不放提示** → 图被转发后，接收者找不到入口

## 八、代码地图

| 文件 | 作用 |
|---|---|
| `walkkcal/reply.py` | ★ 返回契约：组装 `text / meta / next`（三段式文案） |
| `walkkcal/hints.py` | ★ 动态生成 `next`（从当前数据算最值得提示的方向） |
| `walkkcal/select.py` | 选店规则 + 翻页（`order()` 稳定全序 → `pick(page)` 切片） |
| `walkkcal/filter.py` | 业态归类（12 个业态，判定序 type三级 > type二级 > keytag > 店名；「西餐」是聚合键） |
| `entry/mcp_server.py` | MCP：参数 + 描述（**给 Agent 的说明书**） |
| `entry/bot.py` | Bot：inline 按钮 + `callback_data` |
| `SKILL.md` | Skill：参数映射 + 追问规则（给 Agent 的对话脚本） |

**三个入口共用一条流水线**（`entry/mcp_server.py` 的 `_pipeline()` 与
`entry/bot.py` 的 `pipeline()` 逻辑一致）：抓店 → 截断 → 选店 → 文案 → 选项。

## 九、输出形态判据：什么时候**不该**出图（2026-10-15 落地）

上面第三节说了「一次调用返回四件套」，但**没说什么时候连图都不该有**。
契约里 `image` 本来就是可选的（`build(..., image=None)`）、MCP 入口本来就不出图、
`describe_store()` 早就是纯文字模式 —— 三件事同时存在，却**没有一条写下来的判据**。

**现在有了**（`walkkcal/reply.py::choose_mode`）：

> **★ 需要同时比较 ≥2 个对象 → 出图；只有一个对象或一个事实 → 纯文字。**

| 档 | 触发 | 形态 |
|---|---|---|
| `text` | 用户**已收敛**（点名一家店：「就那家」「这家什么好吃」）／候选只有 0~1 家／单点事实（人均、多远） | 纯文字（`describe_store`） |
| `poster` | 用户**要比较**：零参数触发、换一批、换业态、换半径 | 图 + 一句话 + 选项 |
| `poster` | 用户要带走／转发 | 图（脚注自带入口） |

**为什么是这条判据（外部依据）**：

- **ChatGPT 的「智能界面」**（GPT-6）的核心设计就是**由模型判断何时需要界面**：
  「该给图表时只给文字，用户觉得不方便；**只需一句话时却弹出一整套界面，又多此一举**」
- **MCP 规范**：图片块建议加 `annotations.audience=["user"]`（只给界面看）——
  一张 1080p 图的 base64 约 **12,000 token**，且会留在上下文里污染后续每一轮。
  **图片是给人的交付物，不是给 Agent 的返回内容。**
- 认知负荷研究：视觉的优势场景是**信息量大 + 需要比较**（并行扫视）；单点事实用图是过度交付

**落地**：`meta.mode` 由 `build()` 自动写入，三入口共用；`entry/bot.py` 据此决定是否渲染
（`if with_image and payload['meta'].get('mode') == reply.MODE_POSTER`）；
MCP 入口在返回里显式声明「本入口不返回图片，mode 是给最终用户的建议形态」。

**不要反向过度**：图是「转发」这个场景的**唯一解**（脚注就是为转发设计的），
不要为了省事把所有场景都降级成文字。

★ 顺带（同一轮）：**店名里标了「暂停营业/已关闭」的店现在会被剔除并如实计数** ——
地图源没有营业状态字段，但偶尔写进店名（全库 5475 条命中 2 家 ≈0.07%）。
见 `docs/设计取舍.md` 第 19 节。
