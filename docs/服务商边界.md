# 服务商边界 —— 哪些地方换了地图/语料就会跑不通

> **本文给谁看**：想换数据源的人（换地图 / 换语料 / 接自家门店库），
> 以及担心「这项目是不是锁死在某一家上」的评委。

---

## 一句话结论

**现在换地图 / 换语料 = 加 1 个文件 + 设 1 个环境变量，主流程改 0 行。**

而且这件事有**可执行证明**：`tests/test_gate.py::test_map_swap_end_to_end`
造了一家**假地图**（私有类目词「和食 / 烘焙 / 汉堡炸物 / 面食」，故意一个都不与高德相同），
换上去把整条链路跑一遍 —— 跑得通才算过。

还有 `test_provider_boundary` 做**静态守卫**：用 AST 扫通用层模块里
「非 docstring 的字符串常量」，出现服务商私有词汇就**fail**。

## 二、★ 最容易出错的地方：快照有三套互不相同的字段名（已修）

这是**换地图必炸**的地方，2026-10-13 审计时发现。

| 格式 | 位置 | 字段名 |
|---|---|---|
| ① fetcher 产物 | `datasets/*.json` | `distance_m` / `dish_hints` / `industries` |
| ② 池子 | `examples/default/stores.json` | `walk` / `straight` / `tag` / `type` |
| ③ 详情 | `examples/default/detail.json` | `walk` / `tag` / `keytag` / `atag` / `cost` |

字段名对不上，**后果**：新 provider 产出标准结构 → 读快照的一侧认不出来 → **0 家店**。

### 修法：`walkkcal/snapshot.py`（防腐层）

- 唯一认快照格式的地方；把三套字段名归一化成**一个结构**（`geo.py` 的契约 + `cost`）
- **逐字段兜底**（不是按格式分支）—— 注意：按格式分支时会漏字段
  （行里有 `industries` 就走进标准分支，`walk` 被无视 → 距离全 None → 地图投影崩）
- 旧快照里只有服务商私有类目时，用**注入的翻译函数**现场翻译：
  `read_detail(path, translate=geo.get().industries_of)`
  —— 包调用，provider 提供实现，**谁都不越界**
- 向后兼容：旧快照不用迁移，直接能读

## 四、怎么保证不退化

**两条自动化守卫**（`tests/test_gate.py`）：

### ① `test_provider_boundary` —— 静态扫描

用 `ast` 解析通用层模块，收集**非 docstring 的字符串常量**，
命中禁止词表即失败：

```
amap / 高德 / restapi / 餐饮服务 / 外国餐厅 / 其它亚洲菜 / 餐饮相关场所
detail_info / xiachufang / 下厨房 / xcx_dishes / boohee / 薄荷
dianping / 大众点评 / meituan / 美团 / recipeIngredient / recipeInstructions
```

覆盖模块：`filter.py` `prior.py` `select.py` `reply.py` `hints.py`
`tiers.py` `core.py` `theme.py` `packs/registry.py` `packs/pack_nearby_dining.py`

> **为什么用 AST 不用 grep**：docstring 和注释里**应该**点名服务商
> （那是给人看的解释）。被禁的是写进**逻辑**里的私有词汇。
>
> **为什么 `snapshot.py` 例外**：它的职责就是认识历史字段名 ——
> 这层叫「防腐层」，把旧字段名挡在这里，不让它们渗进业务逻辑。

### ② `test_map_swap_end_to_end` —— 端到端换一家地图

造一份假地图快照（标准结构 + 私有类目词），换假 provider，跑完整链路：
`registry.collect` → `filter.apply`（含聚合键「西餐」）→ `select.pick` → 热量。

**这条测试就是「换百度能跑吗」的可执行答案。**

## 五、遗留（明确不做的，以及为什么）

| 项 | 为什么不改 |
|---|---|
| `batch_heat.py` / `portion.py` 读下厨房 JSONL | 它们是**离线预计算**工具（扫 1.9GB 补热量表），不在 Bot/Skill/MCP 运行时链路上。换个语料源时它们用不上，但也不会被调用。真要接薄荷，直接写 `providers/corpus_薄荷.py` 就行。 |

## 六、★ 并发/QPS：地图配额是按「并发」算的（2026-10-15 实测确认）

> 这一节是收到百度告警短信后补的 —— 值得单独写，因为**这类问题不报错**。

### 事件

```
百度短信：并发量超过上限 3/3，需要回复工单
```

**成因**：百度个人 AK 的**并发上限是 3**。探针脚本循环 `sleep 0.30`
＋ provider 默认 `qps_wait=0.35` ≈ 每秒 3 个请求，**正好贴着上限**跑了几百次。

**关键点**：超并发**不会**立刻报错，只是发短信告警；再严重才拒绝服务。
所以「跑起来没报错」不代表没打满配额。

### 修法：限速器放进 `_call()`，谁都绕不过

`walkkcal/geo.py::RateLimiter`（所有 provider 共用）：

| 机制 | 默认值 | 作用 |
|---|---|---|
| `min_interval` | **1.0 秒/请求** | 并发恒为 1，远低于上限 3 |
| `max_requests` | **300 / 进程** | 保险丝，跑飞时**抛错**而不是静默继续 |
| 限流识别 | `并发/上限/超限/频繁/限速/toofast/qps` | 命中后**长退避**（5s×N），连续失败带可操作提示退出 |

```bash
BAIDU_MIN_INTERVAL=2   BAIDU_MAX_REQUESTS=1000   # 想调就调
AMAP_MIN_INTERVAL=2                              # 高德同理
```

**为什么必须放在 `_call()` 里**：只要有一条调用路径忘了自己 sleep
（例如**逐店校正步行距离**那段，原来写死 `sleep 0.2` ≈ 5 请求/秒），
就会瞬间打满并发。放在 `_call()` 里，包括将来新增的调用方都绕不过。

### 顺带修的两处

1. `fetch_pois_at.py` 的 `--scene` 逐店校正循环 `sleep 0.2` → **删掉**，交给限速器；
   并改成显示预计耗时（`N 家 × 1.0s ≈ X 分钟`）。
2. 百度的多关键词检索从 **6 个词 → 4 个**（实测「小吃/火锅」在「美食+餐厅」
   之后新增 0 家，多搜只是多花请求），且**本页无新增就停止翻页**。

### 教训

> **个人 Key 的 QPS 假设必须保守到「宁慢勿快」。**
> 配额按并发算，不是按总量算；超了往往只是「悄悄降级 + 发短信」。

## 九、替代平台调研：「推荐菜」到底谁能给（2026-10-15）

> 起因：百度实测**没有推荐菜**字段。于是要回答「换一家平台行不行」。

### 结论：地图里只有一个能给推荐菜，就是高德

| 平台 | 门店基础 | 业态类目 | **推荐菜** |
|---|---|---|---|
| **高德** | ✅ | ✅ | ✅ `tag`，官方定义「主要出现在美食类POI中，**代表特色菜**」 |
| 百度 | ✅ | ✅（`classified_poi_tag`）| ❌ 实测 `detail_info` 无任何菜品字段 |
| 腾讯位置服务 | ✅ | ✅ | ❌ 字段表只有名称/地址/坐标/类别/电话 + 部分 POI 的营业时间/评分 |
| 美团 · 大众点评 | ⚠ 仅自家/授权商户 | ⚠ | ⚠ **接口真的存在**，但只覆盖**已授权商户** |
| Google Places | ✅（不覆盖中国大陆）| ⚠ 只有粗类目 | ❌ 只有 `servesLunch/servesVegetarianFood` 这类**布尔属性**，没有菜品目录 |

**高德为什么有**：它的 POI 详情里塞了**口碑/点评类内容**。
这是内容资产的打包，不是地图的通用能力 —— 所以别家没有是常态，高德有才是特例。

### 「百度找店 + 换平台拿菜」这条路：技术上可行，但收益为负

做法：百度/腾讯拿门店列表 → 按「店名 + 坐标」反查高德 POI 取 `tag`（跨源实体对齐）。

| 项 | 评估 |
|---|---|
| 可行性 | ✅ 技术上是常规做法（模糊匹配 + 坐标校验）|
| 成本 | 请求数翻倍（每店多 1 次），且要加一层**对齐准确率**校验 |
| **收益** | ❌ **为负** —— 百度在 K11 600m 只召回 50 家，高德 196 家。用召回更差的一侧打头，再回头求高德补菜，**中间白掉一跳** |
| 合规 | ⚠ 跨平台实体对齐属于灰色（但技术上不算违规抓取，因为两边都是自家 Key 的正常接口）|

**唯一合理的方向是反过来的**：用别的源（腾讯/众包）去**补高德漏掉的店**，
而不是拿它们替代高德。

### 美团/大众点评的菜品接口：能查到，但用不上

实测端点确实存在（`developer.meituan.com`）：
`rms/pos/api/v1/chain/goods/query`（总部-获取菜品）、
`wmoper/ng/food/queryFoodList`（门店菜品列表）。

但：

- 全部标注 **「需要业务授权」**
- 语义是**商家自己的门店**（入参 `app_poi_code` = 你的门店 ID），
  **不是「查附近任意一家店的菜」**
- 想做平台级「附近任意餐厅的推荐菜」→ 需要**本地生活数据商务合作**，
  不是注册个开发者账号能拿到的事

⚠️ **不要去爬点评网页**：违反 ToS、反爬极强，且参赛项目一旦被贴上这个标签，
是**负分**（比数据少更糟）。

### 所以真正该做的三件事（按性价比）

| # | 做什么 | 为什么 |
|---|---|---|
| 1 | **把高德固定为第一顺位**（现状），并把「为什么是高德」写进文档 | 这是**选型论证**，不是巧合。评审看得见 |
| 2 | 百度当**降级/备用**（已实现 `provides_dishes=False` 的降级模式）| 高德 Key 不可用时仍能出图 |
| 3 | ★ **挖百度独有的场景标签** | `atmosphere` = 朋友聚餐/情侣约会/商务宴请，`featured_service` = 有包厢/有酒精饮料。**这是高德没有的**，是百度唯一可能反超的地方 |
| 4 | 长期：自建菜品层 `packs/pack_community_menu` | 众包/店家自填「店名+菜名」。零依赖、完全合规、**真正属于你的护城河** |

> **架构上已经准备好了**：`provides_dishes` 能力位 + 降级模式，
> 就是为了「不同源给不同层的数据」。百度实测把这个设计验证了一遍。

## 十、「让用户授权自己的点评账号」这条路（2026-10-15 评估）

> 起因：看到 `github.com/qianwj/dp-mcp` 这种形式 —— 用户登录自己的大众点评账号，
> 程序复用登录态去取数据。**可行吗？**

### 先看它到底怎么做的（我读了仓库）

| 项 | 做法 |
|---|---|
| 技术 | **Playwright 驱动本机 Chrome**，复用**持久化 profile**（`~/.dianping-mcp/browser-profile`）|
| 授权 | 用户自己跑 `npm run login`，在真浏览器里登录并过安全验证 |
| 合规声明 | 明确写「**不使用未经授权的接口，也不试图绕过验证码或反爬机制**」 |
| 节奏 | `DP_MIN_INTERVAL_MS=1500` + 5 分钟内存缓存 |
| 工具 | `search_places` / `get_place_details` / `check_session` |

### ★ 关键发现：它**不提供「推荐菜」**

`search_places` 返回的是：名称、**评分**、**评价数**、**人均**、地址、店铺 URL。
`get_place_details` 返回的是：店铺信息 + **精选评论**。

**没有任何结构化的菜品字段。** 点评网页上确实有「推荐菜」板块，
但这个项目没有提取它 —— 它的定位是「搜索 + 看评论」。

→ **直接接它解决不了我们的核心问题。** 想拿推荐菜，得自己改它去解析网页板块，
而那一步就从「复用登录态」滑向了「结构化抓取」，性质完全变了。

### 法律：有直接判例，而且百度也拿 robots 抗辩过

**大众点评诉百度**（上海浦东法院 2016 一审 → 上海知产法院二审维持）：
百度在地图/知道里大量使用点评内容，判**赔偿 300 万 + 合理费用 23 万**。

判决要点里最该记住的一条：
> 百度**也辩称「抓取行为完全符合大众点评网的 Robots 协议」**，法院**没有采信**。

也就是说 —— **「技术上没被封」≠「合法」**。判决的核心逻辑是**实质性替代**。

**「用户授权自己账号」这一层确实减轻了问题**，但减轻的幅度取决于分界线：

| 场景 | 性质 | 风险 |
|---|---|---|
| 用户**自己**跑脚本、**自己**看结果 | 像「自动化浏览器」，用户访问自己有权访问的内容 | 低 |
| **产品内置**抓取、把结果**聚合展示给所有人** | 落进「实质性替代」的射程 | 高 |

分界线是：**谁在访问、给谁看。**

### 但对我们这个项目，真正致命的是产品层（不是法律）

| 问题 | 后果 |
|---|---|
| 评委不会登录自己的点评账号 | **「克隆即用」直接死掉** —— 而我们刚验证过零配置能跑，这是现成优势 |
| 要装 Node + Chrome + 手动登录 + 过安全验证 | 使用门槛陡增，demo 流程被打断 |
| 登录态过期 / 触发安全验证 / 风控 | **demo 当场挂**，而且你无法控制 |
| 参赛作品内置「绕开某平台正常访问路径」的组件 | 评审印象**负分**（比数据少更糟）|

### 正确落点：不做内置数据源，做**用户自带数据**的口子（已实现）

既然「用户自己有权拿到的数据」可以合法地用，那正确做法是：
**我们只定义数据格式，不提供获取方式。**

`packs/pack_nearby_dining.py` 现在会读可选的 `examples/<场景>/menu.json`：

```json
{
  "味香斋(雁荡路店)": ["麻酱捞面", "小牛汤", "炸猪排"],
  "B0HGZZ273A":      ["红烧牛肉面"]
}
```

- 键可以是**店铺 id** 或**店名**（匹配顺序：id → 完整店名 → 去分店后缀的店名）
- 地图 provider **不提供推荐菜时自动兜底**（`provides_dishes=False`，如百度）
- **热量仍走我们的语料分层** —— 自带表只给「店 → 菜名」，不给卡数
- 你手上的数据怎么来（手工整理 / 自家门店系统 / 委托合规采集）**是你的选择**，
  仓库里没有任何抓取代码

★ **副产品**：这条口子让「**百度找店 + 自带菜品表**」成为一条
**完全不依赖高德**的完整路径 —— 百度那个「没有推荐菜」的限制，
被这一层补齐了。这正是 `packs/` 分层设计的意义。

对照测试见 `tests/test_gate.py::test_local_menu_hook`（含「没有菜品表 → 菜品为空」的对照组）。
