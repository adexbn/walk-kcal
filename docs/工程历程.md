# 工程历程 · 走过的弯路与修正

> **本文给想深入的评委看。**
> 如果只想知道「这产品是什么」，看根目录 [`README.md`](../README.md) 就够了。
>
> 这里记录的是**真实的出错现场** —— 每一处都对应代码里的一次修复。
> 我们认为，**一个项目怎么处理「算错」，比它算得多准更能说明问题。**

---

## 为什么公开这些

做热量工具最容易的，是**给一个看起来正常的数字**。

难的是**知道这个数字什么时候不可信**。

下面这些错误有一个共同点：**算出来的结果都对、值域都对、格式都对 ——
只有拿常识去对，才发现是错的。** 这是我们花最多时间的地方。

---

## 一、数据层：两处最贵的错误

### 1. 语料库 0% 有份量字段

我们抽查了 41896 条菜谱，只有 7 个字段：
`name / dish / description / recipeIngredient / recipeInstructions / author / keywords`

**没有 `recipeYield` / `servings` / `portion`。**

后果：同一道「肉夹馍」，有的配方写 500g 五花肉（是一锅的量），
有的写「适量」。**量级能差 40 倍。**

→ 解法：`portion.py` 按**主料克数反推这道菜做了几份**。

### 2. 【最危险】主料漏算 —— 白斩鸡只有 32 卡

配料表里写「**适量鸡肉**」时，我们的解析器找不到克数 → 主料热量按 0 算。

结果：**白斩鸡 32 卡。**

这个数字格式对、值域对、看起来很正常。肉眼看不出，自动校验也抓不到
（32 卡是合法数值）。**只有当你知道「白斩鸡不可能只有 32 卡」时，才暴露。**

→ 解法：`quality_gate.py` 加**主料闸** —— 主料热量算不出，直接**弃权**。

> 我们的结论：**A（份量）是偏了，B（主料漏算）是错得看起来很正常。B 更危险。**

## 二、量纲混用（3 倍误差）

热量估算有**三个独立量纲**，必须分别处理：

| 量纲 | 典型错误 | 倍数 |
|---|---|---|
| **份量** | 「1只鸡」按量词默认 150g 算 | 少算 **10 倍**（实际 1500g） |
| **小件** | 「10只鸡爪」按整只算 | 多算 **100 倍**（15000g） |
| **生熟密度** | 干面 284 卡/100g vs 湿面约 120 | 差 2 倍 |
| **规格** | 8寸蛋糕 vs 10寸蛋糕 | 原始数据没标 → **弃权** |

→ 解法：`core.py` 的 `UNIT_BY_ITEM` 按**食材**查量词，不用统一默认值。

## 三、匹配错误（错得最像真的）

### 「双层深海鳕鱼堡四件套」= 麦香鱼？

用双向包含匹配（`name in k or k in name`）时，
「双层深海鳕鱼堡四件套」被匹配到了「麦香鱼」。

**两笔订单都显示 472 kcal —— 数字完全合理，实际差 160 kcal。**

→ 解法：必须按 `productCode` 精确匹配，不能只靠名字。

### 「奥灶面」= 「奥利奥面包」？

模糊匹配时，两者都有「奥」字 → 面包的 618 卡被当成了面的热量。

→ 解法：判据收紧为**首字相同 + 一半字符重合**。

### 大饭店的「假绿」

大饭店的推荐菜带品牌/修饰前缀（如「千年古盐田盐焗文昌鸡」），
语料库里既没有整名、也没有裸名 → 全部判「算不出」→ 显示成低热量。

→ 解法：**尾部子串回退** —— 中餐菜名 =「做法/修饰 + 主料」，
主料在**尾部**，取尾部子串去语料库找。命中 19/24，补回 13 条真实值
（桂花红烧肉 745 卡、老上海熏鱼 539 卡…）。

## 五、工程实现

| # | 坑 | 教训 |
|---|---|---|
| 1 | 手写 SVG 用 `%` 拼接，**格式符个数不匹配时 Python 报错指不到那行** | 自建 `OList` 容器，报「第 N 行：格式符 11 个 vs 参数 13 个」 |
| 2 | 长字符串拼接**漏闭合标签**（同一坑连犯 3 次） | `%` 拼接先写完再拆行 |
| 3 | 手写 SVG **没有视口裁剪**，顶点跑出 viewBox 被砍 | 先在数学坐标算顶点，再用 `_fit` 缩放居中 |
| 4 | 「四象限没餐厅」看着像渲染 bug，实为**抓取顺序偏斜** | 改按象限配额抓取 |
| 5 | 圈层半径非线性映射 | `r = (m/R)**0.75 × R`（近处拉开、远处压缩），且有两条硬约束：覆盖最远值 + 数值易读 |

## 六、我们最看重的三条原则

1. **最危险的情况是「数字看着正常」。**
   必须拿常识期望值做校准集逐条对 —— 白斩鸡 32 卡就是这么抓出来的。

2. **算不出就弃权，不猜。**
   「算不出」是一个**正式输出状态**，不是 bug。
   我们宁可 96% 弃权，也不要 65% 错误。

3. **先怀疑量纲，别先怀疑算法。**
   大多数「算错了」，根因是份量/密度/规格混用，不是公式写错。

## 七、误差的最终结论

跑 24 道校准菜，四种聚合方式对比：

| 方式 | 平均相对误差 |
|---|---|
| 中位数 | **28.0%** |
| 均值 | 25.2% |
| 截尾均值 | 25.4% |
| 加权平均 | 25.4% |

**四者只差 3 个百分点 → 换算法救不了数据源。**

我们现在用**中位数**（对离群值稳健 + 最好解释），
并在界面明确标注误差范围。
